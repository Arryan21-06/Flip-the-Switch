1. The problem

Picture a normal morning. Three people are about to type out what they did yesterday, even though the commits, pull requests and issues that show it already sit in GitHub. Meanwhile a pull request has been waiting for review for 31 hours, and nobody has said anything, because nobody wants to be the one who nags.

“We spent the first 20 minutes of every morning recounting git logs that were already written, while critical PR reviews quietly stagnated for days because nobody wanted to be the nag.”

We kept the problem narrow on purpose. Daybreak targets two things:

TodayWith Daybreak
Collecting updatesPeople write or speak updates by hand, though GitHub already records much of the work.Scribe drafts each person’s update from recent GitHub activity, with links to the evidence.
Chasing reviewsA review request waits or CI stays red until someone notices and asks.Sentinel flags it against a rule and drafts a nudge. A human decides whether it goes out.

2. How Daybreak works

Daybreak runs in a shared Switch room, which is the team’s coordination space. Rules, decisions and approvals are meant to live in that conversation. Three agents work in the room:

AgentJobBoundary
ScribeDrafts per-person daily updates from recent GitHub activity and attaches evidence links.Read-only. Does not invent work when there is no activity.
SentinelChecks for potential blockers and proposes follow-up actions.Recommends only. Does not write to GitHub.
ClerkCarries out approved GitHub comments, labels and review requests, then returns the result links.The only write-capable role. Acts only after explicit human approval.

Scribe drafts, Sentinel recommends, Clerk acts only after human approval.

  1. GitHubOpen PRs, issues and commits from the last 24 hours.
  2. Switch roomRules and decisions that every agent reads.
  3. Scribe, SentinelPost the brief, then numbered proposals in the thread.
  4. HumanReplies approve, skip or snooze.
  5. ClerkPosts approved actions to GitHub and returns links.

The evidence principle is No link, no claim. Every statement about someone’s work links to the GitHub activity behind it. If there is none, the brief says “No activity found” instead of inventing status.

The scope is deliberately small: one GitHub repository, one chat room and three agent roles.

3. Why Switch

A cron job and a webhook could post a digest. What they cannot do is give several specialised agents one shared room where the team can change the rules in plain language and approve actions in the same place. That room is why we built on Switch instead of a script.

In our design, agents read the room’s rules on every run. Scribe and Clerk run on Claude Code while Sentinel runs on Codex / OpenCode, sharing the room's persistent rules and state.

The test we care about most is the Friday rule. We tell the room “no nudges on Fridays”, run the workflow again, and verify that Sentinel respects it and suppresses outbound proposals.

Approvals also happen in the room. Our demo client is Mattermost, which is bundled with Switch.

4. Engineering decisions

  • Evidence handling. Updates link to supporting GitHub activity. Missing activity is reported, not filled in.
  • Permissions. Scribe and Sentinel are read-only. Clerk is the only agent with write scope, limited to comments, labels and review requests.
  • Approval gate. A human replies in the thread to approve, skip or snooze each proposal. Nothing is posted to GitHub before approval, and posted comments name who approved them.
  • Duplicate prevention. Each proposal has an ID built from type, target and date, such as nudge-pr42-2026-11-07. Clerk refuses IDs it has completed, preventing double comments on duplicate approvals.
  • Trade-offs. One repo, one room, three roles. The workflow is triggered on demand via webhook or chat command.
  • Non-goals. Agents do not change code, merge pull requests or assign work.

Security and setup

A fine-grained GitHub token limited to the demo repo, with read scope for Scribe and Sentinel and write scope only for Clerk. Secrets live in .env, with .env.example in the repo. Setting DAYBREAK_DRY_RUN=1 makes Clerk print what it would do.

5. What we learned and what’s next

Building a human-in-the-loop multi-agent engineering workflow taught us where autonomous agents shine and where deterministic code must hold the line.

Lessons and limitations

  • Code decides, agents explain. Delegating unconstrained decisions or alerts to an LLM creates alert fatigue. Strict Python heuristics determine what is stuck; agents excel at summarizing and conversing with humans.
  • Cryptographic idempotency in chat. When humans approve actions in chat threads, duplicate clicks or retries can post duplicate comments. Binding each approval to an immutable SHA-256 digest guaranteed exactly-once GitHub execution.
  • Switch integration reality. Level 2 (single-agent multi-role) and Level 1 (CLI) are fully automated and verified via 87 tests. Level 3 declarative room templates are configured and ready for the Switch Console.

Next: roadmap, not shipped
